This is byte-identical to the string already in this repo's `client/public/card-data.json` entry for `"statecraft"` (same `scryfall_oracle_id`), so the premise is confirmed against both an independent authoritative source and the repo's own data. No paraphrase risk.

## Bug summary (root cause, independently reproduced)

`crates/engine/src/parser/oracle_replacement.rs::parse_damage_prevention_replacement` compiles Statecraft's ability into a `ReplacementDefinition` with `valid_card: None`, `damage_source_filter: None`, `damage_target_filter: None` — i.e. **no scoping at all**. Reproduced two ways:

1. **Shipped data**: `client/public/card-data.json["statecraft"].replacements[0]` has `"valid_card": null` (verified via `jq`/`python3 -m json.tool` against the real file, not a snapshot).
2. **Live parser**: calling `parse_oracle_text()` in this checkout with Statecraft's exact string produces the identical shape (`valid_card: None`, `damage_source_filter: None`).

Two independent parsing gaps compound to cause this:

### Gap A — `parse_damage_source_filter` only recognizes ACTIVE voice

`crates/engine/src/parser/oracle_replacement.rs:7409-7454`:

```rust
fn parse_damage_source_filter(norm_lower: &str) -> Option<TargetFilter> {
    let (_, (subject, _)) = nom_primitives::split_once_on(norm_lower, "would deal").ok()?;
    ...
```

This anchors on the literal substring `"would deal"` (active voice: `"<SUBJECT> would deal damage..."`). Statecraft's text is **passive voice** — `"...would be dealt to and dealt by creatures you control"` — which never contains the substring `"would deal"` (`"deal"` vs `"dealt"`), so `split_once_on(..., "would deal").ok()?` fails immediately via the `?` and the function returns `None` before ever looking at what follows `"dealt by "`.

**This is not Statecraft-specific.** Confirmed against the current shipped `card-data.json` for other cards using the same passive `"...would be dealt by <X>"` construction with no "and dealt to" ellipsis at all:

| Card | Oracle clause | Current `valid_card` |
|---|---|---|
| Candletrap | "Prevent all combat damage that would be dealt by enchanted creature." | `null` |
| Defang | "Prevent all damage that would be dealt by enchanted creature." | `null` |
| Charm School | "Prevent all damage that would be dealt to you by sources of the chosen color." | `null` |

Charm School's `"you"` recipient IS correctly captured elsewhere (`parse_damage_prevention_replacement`'s `"dealt to you"` branch, line ~10641), so its `null` `valid_card` is purely the *source*-side ("by sources of the chosen color") falling through Gap A — an independent confirmation that Gap A is the general, not the ellipsis-specific, defect.

**Correction from plan review round 1:** Charm School's source subject, "sources of the chosen color", is **not actually fixed by Gap A**, despite matching Gap A's new passive-voice anchor. `parse_damage_source_subject_filter` (`oracle_replacement.rs:7472-7495`) has no qualifier arm for "of the chosen color" — verified directly: `parse_damage_source_subject` (`7502-7545`) only recognizes the literal `tag("of the chosen type")` (line 7529), and `parse_type_phrase` (`oracle_target.rs`) only recognizes "of the chosen type" too (`oracle_target.rs:3332`, mapping to `FilterProp::IsChosenCreatureType`) — never "of the chosen color" (`FilterProp::IsChosenColor` exists and is used elsewhere, e.g. `game/filter.rs:5988-5989`, but is not wired into this grammar). So after Gap A, Charm School's `parse_damage_source_subject_filter("sources of the chosen color")` still returns `None` — identical to today, **no regression, but also not a claimed fix**. Charm School is moved to "Out of scope, explicitly" below; a genuine fix needs a new "of the chosen color" qualifier arm, which is a separate, smaller follow-up.

### Gap B — the "dealt to and dealt by X" ellipsis is hardcoded to `SelfRef` only

`crates/engine/src/parser/oracle_replacement.rs:10684-10705` already recognizes the elliptical construction "prevent damage dealt to and dealt by X" where the trailing object X is shared between the "to" and "by" clauses (English ellipsis: the object of "dealt to" is elided because it's identical to "dealt by"'s object) — but **only** for the literal self-reference forms (`"~"`, `"this creature"`):

```rust
let valid_card_filter: Option<TargetFilter> = if nom_primitives::scan_contains(working_lower, "dealt to ~")
        || nom_primitives::scan_contains(working_lower, "dealt to and dealt by ~")
        ...
{
    Some(TargetFilter::SelfRef)
} else { ... }
```

For any non-self X — a population filter ("creatures you control": Statecraft) or an attached-host reference ("enchanted creature": Gaseous Form, Ghostly Possession, Sandskin, Heart of Light, Winter's Chill's "that creature") — this branch does not fire, and the generic fallback (`parse_damage_recipient_valid_card_filter`, anchored at a literal `"dealt to "` prefix) also fails, because the text immediately after `"dealt to "` is `"and dealt by ..."`, not a recipient description.

**Confirmed against shipped `card-data.json`** — every card using this ellipsis with a non-self, non-attached-host subject has `valid_card: null`:

| Card | Oracle clause | `valid_card` |
|---|---|---|
| Statecraft | "...dealt to and dealt by creatures you control." | `null` |
| Gaseous Form | "...dealt to and dealt by enchanted creature." | `null` |
| Ghostly Possession | "...dealt to and dealt by enchanted creature." | `null` |
| Sandskin | "...dealt to and dealt by enchanted creature." | `null` |
| Heart of Light | "...dealt to and dealt by enchanted creature." | `null` |
| Winter's Chill | "...dealt to and dealt by that creature." | `null` |

Even Fog Bank (self-ref: `"prevent all combat damage that would be dealt to and dealt by this creature"`) gets `valid_card: SelfRef` correctly for its **recipient** half, but per the architecture note below, its **source** ("dealt by") half is *also* unenforced today — invisible only because Fog Bank is printed 0/4 and never deals nonzero combat damage. This is the same defect as Statecraft's, just harmless for this one card by coincidence of stats, not by design. It is direct evidence this bug has existed for the ENTIRE "dealt to and dealt by" card family, not merely the population-filter subclass.

**Correction from plan review round 1 — Fog Bank regression, now fixed by unifying the self-ref case into the general two-definition path (see Architecture and Step-by-step below).** The original plan draft left the existing self-ref-only branch (`10684-10705`) untouched, reasoning that Gap A's new passive-voice recognition would separately cover the self-ref "by" half through the *ordinary single-definition* path. That is wrong and was a regression risk: `parse_damage_source_filter` runs *unconditionally* inside the same function that also sets `valid_card: SelfRef` from the untouched branch (`oracle_replacement.rs:10732` vs. `10785-10787`), so after Gap A both fields would land on the *same* `ReplacementDefinition` — `valid_card: SelfRef` AND `damage_source_filter: SelfRef` — which (per the Architecture section) means AND semantics: the event's recipient AND source would both have to be Fog Bank, which never happens in real combat (Fog Bank is never its own attacker). That would silently break Fog Bank's currently-correct recipient-side shield. **Fix:** the self-ref ellipsis case is folded into the *same* new bidirectional recognizer as the general case (Step-by-step, below) — every "dealt to and dealt by X" subject, self-ref included, gets its own two independent `ReplacementDefinition`s, and the old self-ref-only branch at `10684-10705` is narrowed to drop its `"dealt to and dealt by ~"` arm (its other four single-direction self-ref checks — `"dealt to ~"`, `"deal damage to ~"`, `"~ would be dealt"`, `"this creature would be dealt"` — are untouched; none of those contain a "dealt by" clause, so Gap A cannot fire on them and there is no equivalent collision risk to fix). Net effect: Fog Bank moves from "recipient-only, harmless-by-luck" to "both halves correctly enforced" — an *additional* confirmed fix, not merely a guarded regression.

**Out of scope, explicitly:**
- Charm School ("...dealt to you by sources of the chosen color") — see the Gap A correction above: its source subject needs a new "of the chosen color" qualifier arm that doesn't exist in the reused grammar. Not touched by this fix; not regressed either (stays exactly as broken/working as today).
- Winter's Chill ("...dealt to and dealt by that creature") — its subject, "that creature", is a demonstrative anaphor to an earlier spell target, resolved via a structurally different mechanism (`parse_anaphoric_target_ref`/`parse_target`'s `ParentTarget` binding, gated on a live `ParseContext`) than the attached-host/typed-filter grammar (`parse_attached_host_subject`/`parse_type_phrase`) this plan reuses. Verified: none of the reused helpers recognize "that creature", so it is not fixed by this change. Also not regressed — stays exactly as broken as today. A genuine fix needs anaphor-resolution wiring into the damage-prevention parser, a separate follow-up.
- Blessed Sanctuary ("...dealt to you **and creatures you control**") — a *different* grammatical shape: a compound **recipient list** joined by "and" within a single "dealt to" clause (not a to/by split). Also `valid_card: null` today, but a distinct parsing gap; fixing it is not required to fix Statecraft and is left as a documented sibling gap, not silently dropped.
- Cephalid Illusionist, Delirium, Dovin/Kiora planeswalkers, Ebony Horse, Elvish Scout, Maze of Ith, and the other *activated-ability* "Prevent all combat damage that would be dealt to and dealt by X this turn" cards — these compile via the **spell/effect** path (`Effect::PreventDamage`, `game/effects/prevent_damage.rs`, `parser/oracle_effect/`), a structurally separate one-shot-shield mechanism from the **static-ability replacement** path this plan touches (`parser/oracle_replacement.rs`, `ReplacementDefinition`). Their `replacements: []` in card-data.json confirms they never reach this code at all. Auditing that separate path is a different investigation and explicitly out of scope here.

## Architecture — why this needs TWO `ReplacementDefinition`s, not one

Read `crates/engine/src/game/replacement.rs:6708-6789` (`object_replacement_candidate_applies`), the function that decides whether a `ReplacementDefinition` matches a proposed `Damage` event. Three relevant fields, each independently gating (`if let Some(...) { if !matches { return false } }` — i.e. **AND** semantics when more than one is set):

- `valid_card: Option<TargetFilter>` (line 6721) — resolves via `event.affected_object_id()`. For `ProposedEvent::Damage`, `affected_object_id()` (`types/proposed_event.rs:1187-1190`) returns `Some(target_object_id)` when the target is an object, **`None` when the target is a player** (so a `valid_card` check can never match player-targeted damage, structurally). It only ever inspects the **recipient**.
- `damage_source_filter: Option<TargetFilter>` (line 6759) — explicitly documented "CR 614.1a: damage-source filters match the damage source object," checked against `source_id`. It only ever inspects the **source**.
- `damage_target_filter: Option<DamageTargetFilter>` (line 6782) — a second, `DamageTargetFilter`-typed recipient scope (supports `Player{scope}`, unlike `valid_card`).

`valid_card` and `damage_source_filter` inspect **two different objects** (recipient vs. source) and are ANDed if both are set on the same `ReplacementDefinition`. Statecraft's ability needs **OR** semantics across those two roles — "prevent this damage if the recipient is a creature I control, OR if the source is a creature I control" — independently, not simultaneously (setting both fields on one definition would wrongly require *both* to be true on the *same* event, i.e. only prevent damage a controlled creature deals to another controlled creature — far narrower than the card says, and precisely wrong for the reported bug, where the recipient was the *opponent player*, never an object at all).

The engine already resolves this exact shape of problem by registering **multiple independent `ReplacementDefinition`s**, each a separate "candidate" `find_applicable_replacements` considers — the OR emerges naturally at the Vec level, not by cleverness inside one definition.

## Analogous Trace (Gate B anchors)

1. **`crates/engine/src/parser/oracle.rs:6040-6057`** — `lower_as_enters_or_face_up_counters`, called from the main per-line static/replacement dispatch loop. Comment: *"A single sentence that never splits on `.`, so it needs a multi-emit-into-`result` path (one `Moved`/Battlefield + one `TurnFaceUp` replacement sharing the PutCounter execute). Runs BEFORE the generic sequence/line parsers, whose per-arm parsers each return one definition and cannot emit the dual pair."* This is the **exact same shape** of problem: one physical Oracle sentence, no internal period, that must lower to two independent `ReplacementIr`s. Traced end to end: `lower_as_enters_or_face_up_counters(&line) -> Option<Vec<ReplacementIr>>` → `for replacement_ir in replacement_irs { emitter.replacement_ir_at(item_line, replacement_ir); }`.
2. **`crates/engine/src/parser/oracle.rs:229-250, 6065-6072`** — `parse_replacement_sentence_sequence_ir(line, card_name) -> Option<Vec<ReplacementIr>>`, the sibling multi-*sentence* (2+ period-terminated clauses) variant of the same "one line → many replacements" shape, consumed the same way: `for replacement_ir in replacement_irs { emitter.emit_at(item_line, OracleNodeIr::Replacement(replacement_ir)); }`.
3. **`crates/engine/src/parser/oracle_replacement.rs:10684-10705`** — the existing (self-ref-only) "dealt to and dealt by ~" branch this plan *replaces* (its `"dealt to and dealt by ~"` arm only; its other four self-ref arms are untouched, see the Fog Bank correction above). Same file, same function (`parse_damage_prevention_replacement`), same `valid_card_filter` local — read for its subject-extraction shape, then superseded by the new unified two-definition recognizer for this one arm.
4. **`crates/engine/src/parser/oracle_replacement.rs:7472-7495`** — `parse_damage_source_subject_filter`, the existing helper that already turns a bare subject string ("creatures you control", "enchanted creature", "a creature") into a `TargetFilter` via `parse_attached_host_subject` then `parse_type_phrase`. Reused as-is for both Gap A's fix and Gap B's generalization — no new filter-parsing logic needed, only new anchoring/dispatch.

## Building Blocks

- `nom_primitives::split_once_on` — already used by `parse_damage_source_filter`; reused for the new passive-voice anchor.
- `nom_primitives::scan_at_word_boundaries` — already used by `parse_damage_recipient_scope` / `parse_damage_recipient_valid_card_filter`; reused to locate `"dealt by "` anywhere in the clause (needed because it can be preceded by "would be", "is", or (for the ellipsis) "and dealt").
- `parse_damage_source_subject_filter` (`oracle_replacement.rs:7472`) — turns the isolated subject string into a `TargetFilter`; already generic over "creatures you control" / "enchanted creature" / typed filters. No changes needed to this function.
- `scan_combat_scope` (`oracle_replacement.rs:7901-7911`) — **correction from plan review round 4:** already used by `parse_damage_modification_replacement`/`parse_damage_modification_static` (not, as an earlier revision of this plan claimed, by `parse_damage_prevention_replacement` — that function derives the same value via its own inline `scan_contains("noncombat damage")`/`scan_contains("combat damage")` at line 10627, functionally identical per `scan_contains`'s own doc comment, but a different call site). `scan_combat_scope` is reused as-is by the new bidirectional recognizer (added per plan review round 3 — the new function is a standalone dispatch arm and does not otherwise inherit this computation from anywhere); it is the correct existing helper to call regardless of which other function also happens to use it.
- The `all_consuming(alt((eof, tag("."), tag("this turn"), tag("until end of turn"))))` clause-boundary terminator already used in `parse_damage_recipient_after_prefix` (`oracle_replacement.rs:10932-10951`) — reused verbatim as the terminator for the new passive-source extraction, so `"creatures you control."` correctly isolates `"creatures you control"` (not `"creatures you control."`) before handing it to `parse_damage_source_subject_filter`, which requires full consumption.
- `ReplacementDefinition::new(...).valid_card(..).damage_target_filter... .combat_scope(..).prevention_shield(..)` builder methods — reused as-is; no new field/method on `ReplacementDefinition`.

## Logic Placement

All changes live in `crates/engine/src/parser/`:
- `oracle_replacement.rs` — Gap A fix (passive-voice source extraction) and the new bidirectional-ellipsis recognizer function.
- `oracle.rs` — one new dispatch arm in the per-line static/replacement loop, mirroring `lower_as_enters_or_face_up_counters`'s existing call site exactly.

No changes to `game/`, `types/`, or the frontend — this is a pure parser-compilation fix; the runtime replacement-matching architecture (`game/replacement.rs`) already correctly supports everything the fix needs (confirmed by reading `object_replacement_candidate_applies` above), it just never receives correctly-populated `ReplacementDefinition`s for this Oracle-text shape today.

## Rust Idioms / Nom Compliance

- New function `parse_damage_source_filter_passive` (Step-by-step #2, below), backed by a shared `finish_damage_source_subject` tail factored out of `parse_damage_source_filter` (Step-by-step #1): `nom_primitives::scan_at_word_boundaries` to find `"dealt by "` (mirrors the existing recipient-side scan at `oracle_replacement.rs:10707-10716`), then reuse the existing subject-postprocessing pipeline (`"if "` clause extraction, `"~"` self-check, article-stripping, `parse_damage_source_subject_filter`) currently inlined in `parse_damage_source_filter` — factor that shared postprocessing into the small helper both the active-voice and passive-voice extraction call, rather than duplicating it (`parse_damage_source_filter` currently has ~40 lines of subject postprocessing after the anchor-split; the anchor changes, the postprocessing doesn't). The same `finish_damage_source_subject` helper is reused a third time by the bidirectional recognizer (Step-by-step #4), so all three extraction sites (active, passive, ellipsis) share one postprocessing authority.
- New bidirectional recognizer: `alt()` over the two orderings actually attested in Oracle text (`"dealt to and dealt by "`, and defensively `"dealt by ... and dealt to"` is NOT attested in any sampled card and is *not* added — no speculative grammar), anchored with `tag()`/`preceded()`, never `.contains()`/`.find()`.
- No new `bool` fields. No new enum variants on `ReplacementDefinition`, `TargetFilter`, or `DamageTargetFilter` — the fix is purely in *which* existing fields get populated and *how many* `ReplacementDefinition`s one Oracle clause lowers to.

## Extension vs Creation

Extends two existing patterns (Gap A's active-voice extraction; the "one line → `Vec<ReplacementIr>`" multi-emit dispatch shape already used twice in `oracle.rs`). **Replaces** one arm of a third (the self-ref-only `"dealt to and dealt by ~"` check at `10684-10705` is removed, superseded by the new unified recognizer — not extended in place, per the plan-review-round-1 Fog Bank correction: leaving it as a separate special case is what created the AND-collision risk). Creates one new function pair (passive-source extraction, bidirectional recognizer) that is a straight generalization of existing code, not a new pattern family.

## Identity / Provenance Contract

"Creatures you control" / "enchanted creature" resolve via the **already-correct, already-tested** live `ControllerRef::You` / `TargetFilter::AttachedTo` machinery this investigation independently verified in 8 prior engine-level probes (control-change via both `Effect::GiveControl` and `Effect::GainControl`, save/load round-trip, double-strike, real-cast pipeline — all passed once a correctly-populated filter is actually present). This plan does not touch controller/attachment resolution at all; it only fixes *whether* a filter reaches the replacement definition in the first place. No new selected-authority/binding-time concerns are introduced — `valid_card` and `damage_source_filter` are evaluated live, every time, exactly as every other card using these two fields already relies on.

## CR references (to verify against `docs/MagicCompRules.txt` before landing)

- CR 614.1a — replacement effects using "instead"/"prevent" (the base authority for `ReplacementDefinition`).
- CR 615.1a — "prevent all/the next N damage" (`ShieldKind::Prevention`).
- CR 109.5 — "you" in a static ability's text means that object's controller (already correctly implemented; cited for context only, not modified).
- CR 616.1 — when two or more replacement effects could apply to the same event, the affected player/controller chooses the order (governs the self-damage interactive-choice row in the Verification Matrix, added in plan review round 2; existing engine machinery, not modified by this plan).
