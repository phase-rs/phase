# Chartered runs

Read this when [SKILL.md](SKILL.md)'s phase-fit gate fires (T1 AND T2), and hand the relevant section to every role in a chartered run. Oversized workloads make review loops stop converging: each repair is made against an artifact too large to hold, so repairs generate the next round's findings. The fix is shrinking the unit of review. A chartered run decomposes into sequential phases, each running the full plan → review → implement → review pipeline. The [run limits](SKILL.md#run-limits) apply to every loop here.

## When the gate fires

**T3 — dependency seams (seam-selection rule, not a trigger):** where one unit cannot be discriminating-tested until another lands (infrastructure→consumer), that edge is the preferred split point. Anything T3 would catch has ≥2 units and fires via T1∧T2. Size without split structure (one large unit) and count without size (trivial multi-arm work) both stay single-phase; the conjunction confines false positives to the degenerate large-unit-plus-trivial-unit edge, where the cost is one tiny fast-converging phase.

**Routes when a re-adjudication fires:** **mid-Step-2 on a not-yet-clean draft** → a charter-mode planner derives from the draft + accumulated findings, provided the run limits permit another dispatch. **At scope-freeze on a review-clean plan** → the charter-mode planner **partitions, not re-plans** — the charter carves converged content, each phase plan is a projection of reviewed material, so the split does not invalidate the reviewed artifact. **Inside a chartered phase before its executor dispatch** (its plan loop or its scope-freeze — zero landed candidates either way) → a re-charter splitting that phase. A second-level firing inside an already split phase stops for reassessment. With landed candidates requiring a new split, stop and propose a re-charter through an expansion case rather than restarting or truncating the phase.

**Feasibility exit (the only single-phase path after a firing):** the charter-mode planner may report no green-tree seam exists — every candidate split point named and shown to leave the tree non-compiling or tests red. Record the named evidence in the phase-fit record and proceed single-phase.

A decomposition proposed at a stop (see SKILL.md "At a stop") starts only through an accepted expansion case.

## The charter

Authored by a freshly spawned planner in `engine-planner` **charter mode** (the orchestrator never authors), reviewed through `review-engine-plan` **charter mode** in its own loop. In that loop a round carrying a decision finding is a design round; a round whose findings are all corrections is a clean round — the orchestrator applies them and the charter freezes without a further round. Once clean, the charter's **decisions** are frozen: which phases exist, their order and seams, each phase's goal and the architecture decisions it carries out, what is deferred to which phase, and each phase's addenda file (`<run-root>/addenda/phase-<k>`). The charter is architecture only: acceptance rows and the claims a phase must establish belong to that phase's plan. The charter is recorded at `<run-root>/phase-charter`.

A charter is a contract about architecture and sequencing, not a snapshot of the code. Two things never belong in it, because both change during implementation and each change would otherwise cost a planner round: a **file inventory** — per-phase scope is a scope rule (below), materialized into `SCOPE_PATHS` at scope-freeze — and **code-state assertions** — where a phase depends on how the code behaves today (a defect is live at base, a path is unreachable, a gate observes an outcome), the phase plan names the claim it must **establish** and buys it by measurement; the charter never states the outcome as fact.

**Addenda and re-charter.** Once the charter is clean, drift found during the work is sized against the charter's decisions:

- **Drift that leaves every decision standing is an addendum:** one line in that phase's addenda file, naming the decision it touches, what drifted and why. The orchestrator writes it; no planner or charter review round runs. Typical drift: a `SCOPE_PATHS` extension, a file the phase needs beyond its scope rule, a claim the plan established differently than expected, a defective reference fixed in-phase ([SKILL.md](SKILL.md#defective-reference-route)), a small fix in a file the phase already edits.
- **Drift that breaks a decision the rest of the design rests on is a re-charter**, whether it breaks it alone or together with the earlier addenda on that decision. Before writing an addendum, read the addenda that name the same decision. A re-charter runs the charter-mode planner and the charter review loop over the **remaining** phases, with the addenda that led to it as input. Accepted phases are never reworked in place: content a break invalidates is repaired by a later phase the re-charter names.
- **When in doubt, write the addendum.** The next review of the delivered work can still call it a break.
- **Corrections** (a figure, a citation, wording) are applied by the orchestrator, with no review round.

Each phase's Step 6 implementation review reads that phase's addenda file; the integration review reads all of them. Addenda never go into the charter or a plan.

**There is no phase ledger.** The phase-fit, phase-charter and addenda records carry phase indexes only, never a commit SHA; a SHA-bearing acceptance record would be a parallel ledger. Chain integrity is recomputed at run-level acceptance instead.

## Per-phase identity and the substitution rule

Each phase k is a self-contained checkpoint pipeline with `PHASE_BASE_SHA` — phase 1: run-level `BASE_SHA`; phase k>1: phase k−1's accepted `CANDIDATE_SHA` — and its own scope, fixed at the phase's scope-freeze moment (after its plan loop, before executor dispatch; never before the phase plan exists). Per-phase scopes **may overlap** on shared registration files (`effects/mod.rs` and kin); sequential execution makes that safe — there is no global-partition requirement.

**Scope rule.** The `SCOPE_PATHS` list is materialized at scope-freeze by the orchestrator from the charter's phase entry and the phase plan's Sizing — materialization is measurement, the same category as the gate. Three standing classes are admitted to the list without any revision: files the compiler forces (an exhaustive `match` or constructor the phase's type change breaks), shared registration files (`effects/mod.rs` and kin, the integration-test `mod` list), and files in which no non-comment line is added or removed — together with any committed generated artifact T2 groups with such a file, since a doc comment on a binding-exported type regenerates its binding and CI byte-compares the pair; admit both or neither. A standing class never overrides an explicit out-of-bounds entry in the executor's spawn inputs: extension applies only to a standing-class path that was omitted from the materialized list, and a standing-class path that is explicitly out of bounds takes the ordinary stop-and-return decision path below, never re-dispatch. Every extension re-counts T2 over the extended list and re-evaluates the full T1 AND T2 conjunction; T2 alone never triggers a split. Only when the conjunction fires does the extension take the in-phase route above. An executor that meets one of these outside the list does not edit it — its authorized-path check is unchanged — but stops and returns the site as an admitted-class addition with its evidence (the compiler error, the registration site, the comment-only change it needs); the orchestrator extends `SCOPE_PATHS`, writes the addendum line, then restores the implementation worktree to `START_SHA` and re-dispatches the same round with the extended list and the executor's report as constraints. No planner or charter review round runs; the phase's implementation review checks each extension against its addendum. `RUST_PATHS` and every other list the executor derives from its authorized paths follow the extended list at re-dispatch. An out-of-list file of any other class returns to the phase's plan step, so a planner and its reviewer admit it before any executor edits it or any gate builds it; the revised scope is then sized like any drift: an addendum when every charter decision still stands, a re-charter when it breaks one. T2 re-adjudication at scope-freeze counts the materialized list.

**Within a phase, every occurrence of `BASE_SHA` in SKILL.md's Inputs worktree preparation and Steps 3–7 (checkpoint delta, `scoped_diff_command`, projection worktrees, completion parser-gate range, Step 6 review span) means `PHASE_BASE_SHA`** — the literal `"$BASE_SHA"` command templates stay byte-identical while the shell variable carries the phase base, so checkpoint-mode validation needs no changes. Run-level `BASE_SHA` remains available to seed phase 1's `PHASE_BASE_SHA` and for the final integration span; per-phase operations use `PHASE_BASE_SHA`.

**Per-phase spawn inputs:** all roles also receive the original task and the attempt history. The charter-mode planner and its reviewer, and each phase's Step 1 planner and Step 2 reviewer, receive a precedent pack from the [scout](scout.md), taken at the run base for the charter and at `PHASE_BASE_SHA` for a phase. Step 1 planners run in `engine-planner` **phase-plan mode** with the charter, the phase's entry, its deferral allowlist, and prior phases' accepted summaries (never their debates). Step 2 reviewers run in `review-engine-plan` **phase-plan mode** with the phase plan, the original task, the charter, the phase index, and the allowlist, and declare the phase-fit context so the Sizing consistency check is blocking. Step 3 executors run in [executor.md](executor.md)'s **phase mode** with the charter, phase index, and allowlist, so the matrix and test map they author use the same `DEFERRED(phase n)` vocabulary their reviewers audit. Step 6 reviewers run in `review-engine-impl` **phase mode** with the charter, phase index, allowlist, the phase's materialized `SCOPE_PATHS`, and the phase's addenda file.

## Run-level acceptance (after the last phase)

Per-phase acceptance is SKILL.md's Step 7 applied to the phase, and **emits no Final Report snapshot and no PR-handoff block**; those are run-level only. Run-level final acceptance requires all of:

1. **Every phase accepted** on its own review and checks.
2. **The phases actually tile the run**, checked against git: each phase's accepted candidate is the next phase's base, and `git rev-list <prior accepted>..<phase accepted>` contains only that phase's own commits. Restarted and abandoned candidates legitimately sit outside those intervals — list them in the Final Report rather than forcing the intervals to match.
3. **The integration review returns zero findings**, run in `review-engine-impl` **integration mode** (findings-only; scoped to cross-phase seams and charter completeness). Reviewer inputs: the run-span `BASE_SHA..final CANDIDATE_SHA` diff, charter, every phase's addenda file and attempt history. Findings dispatch a fix phase via re-charter only while the run limits permit. **Bound:** at most one fix phase per integration round; findings still present after two fix phases → stop and surface to the user.

The Final Report additionally lists: phase count; per-phase accepted `CANDIDATE_SHA`s, each correction commit with the reviewed SHA it corrects; abandoned candidates from approved restarts; the phase-charter record path; the chain-integrity result; and the integration-review result.
